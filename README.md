# Kcell Web Backend

FastAPI бэкенд для внутренней системы управления контролями и задачами Kcell.

# Last migration: 9c1dedc8bd2c

## Стек

- Python 3.14
- FastAPI
- SQLAlchemy 2.0 (async)
- PostgreSQL
- Alembic
- Pydantic v2
- JWT (python-jose)
- Argon2 (passlib)

## Установка

### 1. Клонируй репозиторий

git clone <https://github.com/hush0k/kcell_backend.git>
cd backend

### 2. Установи зависимости

uv sync

### 3. Создай .env файл

Скопируй `.example.env` и заполни:

cp .example.env .env

### 4. Примени миграции

./scripts/migrate.sh "init"

### 5. Создай админа

uv run python seed.py

### 6. Запусти сервер

./scripts/run.sh

## API

После запуска документация доступна по адресу:

- Swagger UI: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc

# Запуск сервера под DFS
1. Узнать точный UNC-путь DFS
   У сетевого админа Kcell спросить полный путь папки, например \\kcell.local\dfs\me_notes.
2. Проверить доступ через проводник Windows
   Открыть Win+R → вставить путь → Enter. Если просит логин/пароль — ввести доменные креды (обычно те же, что от рабочего компьютера в домене KCELL). Если папка открылась и видно файлы — доступ есть.
3. Смонтировать как сетевой диск (для удобства, не обязательно)
   Проводник → «Этот компьютер» → «Подключить сетевой диск» → указать UNC-путь → назначить букву (например Z:) → поставить галку «Восстанавливать при входе в систему» (чтобы монтировалось автоматически при каждом включении).
4. Если ноут не в домене Kcell (VPN)
   Убедиться, что VPN-клиент Kcell подключён и активен — без VPN DFS-шара не будет видна вообще.
5. Настройка на стороне бэкенда (FastAPI)
   Если бэкенд крутится тоже на этом же ноуте (или в WSL/Docker на нём):

Windows-хост: путь уже доступен как Z:\ или \\kcell.local\dfs\me_notes.
Если бэкенд в WSL2/Docker — Windows-шары напрямую недоступны из Linux-контейнера; там либо пробрасывать путь через /mnt/z/ (WSL видит Windows-диски автоматически), либо монтировать CIFS отдельно внутри WSL с теми же кредами.

6. Прописать путь в .env
   DFS_ROOT=Z:\me_notes
   или, если через WSL:
   DFS_ROOT=/mnt/z/me_notes
7. Проверить права
   Ментор должен убедиться, что его доменный аккаунт имеет read/write, а не только read — иначе is_editing/сохранение файлов будет падать с permission denied.
8. Тест
   Создать/удалить тестовый файл через проводник в этой папке — если получилось, приложение тоже сможет читать/писать по этому пути.


# Изменения

Все `PUT` заменены на `PATCH` по всему проекту.

---

## Auth

### Что реализовано
- `POST /api/v1/auth/refresh` — выдача нового access token по refresh token
- Refresh token со сроком хранения 100 лет (фактически бессрочный для внутреннего сервиса)

### Что изменено относительно легаси
- Добавлен механизм refresh token — в легаси был только access token без возможности обновления (требовался повторный логин после истечения)
- `PUT` → `PATCH` (общее для всего проекта)

### Архитектурное решение
- Срок жизни refresh token в 100 лет выбран как компромисс для внутреннего корпоративного инструмента без UX-требований к ре-логину — обсудить с ментором, нужна ли более короткая ротация и механизм инвалидации (blacklist токенов через Redis, отложено)

## User

### Что реализовано
- Новый атрибут `is_og` — флаг принадлежности к ОГ (оперативная группа)
- `created_at`/`updated_at` через общий `TimeStampMixin`
- Пагинация в `get_all_users()`, лимит по умолчанию — 20 пользователей
- `POST /api/v1/users` — создание пользователя доступно только админу
- `PATCH /api/v1/users/{id}` — изменение доступно админу или самому пользователю (включая смену собственного пароля)
- `DELETE /api/v1/users/{id}` — удаление только админом

### Что изменено относительно легаси
- Расчёт и заполнение колонки `weekend_group_id` перенесены из Python-кода в функцию PostgreSQL
- Расчёт дедлайна каждой задачи перенесён в функцию БД; для ручного запуска оставлен отдельный backend-эндпоинт
- `PUT` → `PATCH` 
- Добавил два новых полей как fist_name and last_name

### Архитектурное решение
- Группировочная и вычислительная логика (`weekend_group_id`, дедлайны), требующая обхода большого числа строк, намеренно вынесена на сторону PostgreSQL вместо Python-сервиса — соответствует общему архитектурному принципу проекта (БД-функции + `pg_cron` вместо Celery/планировщиков на Python), согласовано с ментором

## Control

### Что реализовано
- `frequency` — полноценный `Enum`, заменяет произвольную строку
- Фильтрация и сортировка в `get_all_controls()` по двум полям: `area` и `control_status`
- Базовая защита всех эндпоинтов — доступ к чтению только для зарегистрированных пользователей
- Проверка роли `admin` на `POST`, `PATCH`, `DELETE`

### Что изменено относительно легаси
- `frequency`: `String(32)` → `Enum`
- `risk` и `priority` намеренно оставлены как простые поля с дефолтным значением `0` — без enum, в отличие от `frequency`

### Архитектурное решение
- Принцип доступа: чтение — любому авторизованному пользователю, запись (`create`/`update`/`delete`) — только админу. Этот паттерн доступа единообразно применяется по всему проекту, не только в Control
- `risk`/`priority` оставлены как простые placeholder-поля до уточнения у ментора их реального смыслового наполнения (возможно, тоже станут enum в будущем)

## Holidays / Non-working days

### Что реализовано
- Новая таблица `non_working_days` — хранит праздничные дни и выходные (суббота/воскресенье)
- Заполнение через скрипт `refresh_non_working_days.py` с использованием библиотеки `holidays` (календарь Казахстана, с поддержкой переноса праздничных дней)

### Что изменено относительно легаси
- В легаси отдельной таблицы выходных дней не существовало — нерабочие дни вычислялись ad hoc внутри кода на каждый случай использования

### Архитектурное решение
- Вынесение нерабочих дней в отдельную таблицу позволяет SQL-функциям генерации задач и расчёта дедлайнов джойниться на неё напрямую внутри PostgreSQL, без обращения к внешним Python-библиотекам на каждый запрос — критично, раз основная логика теперь живёт в БД-функциях

## Vacation Schedule

### Что реализовано
- Полный CRUD переписан на асинхронный сервис
- `vacation_type` и `status` вынесены в `Enum`: `VacationType` (`annual_leave` / `sick_leave` / `business_trip`), `VacationStatus` (`active` / `cancelled`)
- `create`, `update`, `delete` доступны только админу
- `GET get_active_vacations_with_remaining_days()` — список активных отпусков с количеством оставшихся дней
- Функция БД `reassign_tasks_for_vacation()`: если у `original_user` активный отпуск на текущую дату — `control.responsible_id` переключается на `backup_id`; после окончания отпуска возвращается обратно на `original_user_id`
- Внутренний хелпер `_check_for_vacation(user_id)` — проверка активного отпуска через `func.current_date()`

### Что изменено относительно легаси
- `PUT` → `PATCH`
- `vacation_type`/`status`: произвольные строки → `Enum`
- `created_at`/`updated_at`: ручные поля → `TimeStampMixin`
- Логика переключения ответственного на время отпуска перенесена из Python-сервиса в SQL-функцию `reassign_tasks_for_vacation()`, выполняется по расписанию через `pg_cron`

### Архитектурное решение
- Reassign/restore ответственного — классический пример логики, которую нельзя доверять разовому Python-скрипту (нужна гарантированная ежедневная отработка вне зависимости от того, запущен бэкенд или нет) — реализовано как БД-функция + `pg_cron`, согласовано с ментором
- Интеграционные тесты на reassign/restore написаны и проходят

## Task

### Что реализовано
- Поле `deadline_time` (`DateTime` с таймзоной) заменяет легаси-поле `date`. Дедлайн считается от частоты контрола: `daily` → 23:59:59 того же дня, `weekly` → воскресенье, `monthly` → последний день месяца, `quarterly` → последний день квартала, "по запросу" → +100 лет (фактически бессрочная задача)
- `status` вынесен в `Enum TaskStatus` (`not_started` / `in_progress` / `completed` / `cancelled`)
- Генерация задач перенесена в функции БД: `generate_daily_tasks`, `generate_weekly_tasks`, `generate_monthly_tasks`, `generate_quarterly_tasks`, `update_overdue_task_dates`
- `POST /trigger-tasks-generator` — ручной запуск генерации (только админ)
- `complete_task` — переводит задачу в `completed`, проставляет `end_time`; для контролов "по запросу" автоматически создаёт новую задачу
- `weekend_group_id`: при завершении задачи в понедельник `sync_weekend_tasks` автоматически проставляет статус связанным субботним/воскресным задачам
- `start_task` — берёт задачу в работу (`in_progress` + `start_time` + назначение текущего пользователя)
- `get_all` с ролевой фильтрацией: админ видит все задачи, обычный пользователь — только свои
- `get_overdue` по той же логике ролей: админ — все просроченные, пользователь — свои
- Отдельные эндпоинты по статусам: `/not-started`, `/in-progress`, `/completed`, `/overdue`
- `PATCH /tasks/{id}` с проверкой прав: изменять может админ, ответственный (`responsible_id`), бэкап (`backup_id`) либо член ОГ — если задача относится к ОГ
- `get_all_with_controls` — задачи вместе с данными контролов, с пагинацией
- `DELETE` — только админ

### Что изменено относительно легаси
- `date` → `deadline_time` (с расчётом по частоте контрола вместо хранения сырого периода)
- `status`: строка → `Enum TaskStatus`
- `PUT` → `PATCH`
- Генерация задач: Python-логика → SQL-функции + `pg_cron`
- Доступ к списку и просроченным задачам: в легаси не было разделения по ролям, теперь — явная фильтрация admin/user

### Архитектурное решение
- `generate_daily_tasks()` и связанные функции — центральный пример паттерна "вся плановая логика в БД": гарантирует выполнение независимо от состояния backend-процесса, не требует Celery/APScheduler
- Разделение прав на `PATCH` (админ / ответственный / бэкап / член ОГ) — реализовано в сервисном слое, не в роутере, как явная проверка авторства и ролей
- `weekend_group_id` синхронизация по понедельникам — единственный кейс, где завершение одной задачи каскадно меняет статус других; логика сознательно изолирована в `sync_weekend_tasks`, не размазана по `complete_task`

## Incident

### Что реализовано
- Новая таблица `incident` (модель существовала в легаси, в новом проекте отсутствовала — реализована с нуля)
- `status` вынесен в `Enum IncidentStatus` (`Открыт` / `На согласовании` / `Согласован` / `Отклонён`)
- Денежные поля (`estimated_loss`, `opportunity_loss`, `bad_debt` и т.д.) оставлены `Numeric(15,2)` → `Decimal`, как в легаси
- Связь с `Task` через `task_id` (nullable), `relationship` `task` ↔ `incidents`

### Что изменено относительно легаси
- `created_date` убран, заменён на `created_at`/`updated_at` из `TimeStampMixin`
- `status`: строка (свободный текст в легаси) → `Enum IncidentStatus` с фиксированным набором состояний (FSM)

### Архитектурное решение
- `IncidentStatus` реализован как конечный автомат (FSM): переходы между статусами вынесены в отдельный эндпоинт `PATCH /{id}/status`, а не смешаны с общим `PATCH /{id}` для остальных полей — изменение состояния и изменение данных разведены сознательно
- Денежные поля сохранены как `Numeric(15,2)`/`Decimal` по принципу "не трогать финансовые legacy-решения без явного согласования с ментором"

## MFS Audit Log

### Что реализовано
- Модуль `mfs/` с разделением Repository / Service / Router
- `MfsAuditLog` — журнал операций МФС (block/unblock/check) в основной БД `kcell_web`
- `MfsBlacklistService` — операции с blacklist MSISDN через отдельную БД (второй async engine, raw SQL через `text()`)
- `GET /api/v1/mfs_audit_log/` — список логов (admin видит все, обычный пользователь — только свои)
- `GET /api/v1/mfs_audit_log/{id}` — детали записи, доступ по роли/владельцу (403 при попытке чужого)
- `POST /api/v1/mfs/action` — выполнение операции (block/unblock/check) + запись в журнал

### Что изменено относительно легаси
- `action`: `String(16)` → `Enum` (`Action`)
- `results_json`: `TEXT` + ручной `json.dumps/loads` → `JSONB`
- `created_at`: naive `DateTime` (UTC вручную) → `DateTime(timezone=True)`, `server_default=func.now()`
- Убран рантайм-антипаттерн `_ensure_mfs_audit_log_table` — таблица создаётся только через Alembic
- Исправлен баг легаси в `block`: поиск дубликата по `LIKE '%...'` (полное сканирование) заменён на точное `=` (номер уже нормализован)
- Подключение к blacklist-БД: синхронный `psycopg2` → асинхронный `asyncpg` через отдельный `mfs_engine`
- POST-эндпоинт создания лога публично не выставлен — запись пишется только как сайд-эффект `/mfs/action`, чтобы исключить подмену `user_id`/`results`

### Архитектурное решение
- `mfs_audit_log` иммутабелен: нет `update`/`delete`, нет схемы `MfsAuditUpdate`
- Сбой записи в журнал не блокирует саму операцию над blacklist — пользователь получает `audit_warning` в ответе (поведение легаси сохранено)
- `MfsBlacklistService` и `MfsAuditLogService` работают с разными БД через разные `AsyncSession`, без общей транзакции (намеренно — физически разные базы)

## Notification

### Что реализовано
- Модуль `notification/` с разделением Repository / Service / Router
- `Notification` — таблица уведомлений с полями `title`, `html_content`, `recipients_email` (строка через `;`), `notification_type`
- `NotificationRecipient` — junction-таблица: одна строка на каждого получателя, хранит независимый `is_read` и `read_at`
- `ConnectionManager` — in-memory словарь `dict[int, list[WebSocket]]`, хранит активные WS-соединения по `user_id`
- `pg_notify_listener` — фоновая задача (asyncpg), слушает канал `new_notification` и пушит онлайн-юзерам через WS
- `GET /api/v1/notifications` — список уведомлений текущего юзера с пагинацией (joinedload notification)
- `GET /api/v1/notifications/unread-count` — количество непрочитанных
- `GET /api/v1/notifications/{id}/html` — HTML-контент уведомления
- `POST /api/v1/notifications/{id}/read` — пометить как прочитанное
- `WS /api/v1/notifications/ws?token=...` — WebSocket эндпоинт, JWT передаётся query-параметром

### Что реализовано относительно легаси
- Real-time доставка уведомлений через WebSocket + `pg_notify` вместо polling
- `recipients_email` парсится в `user_ids` на лету через `get_user_ids_by_emails()`
- `is_read` перенесён на уровень `NotificationRecipient` — каждый юзер имеет независимое состояние прочтения
- PostgreSQL триггер `on_new_notification` на таблице `notification` автоматически вызывает `pg_notify` при каждом INSERT

### Архитектурное решение
- `asyncpg` используется отдельно от SQLAlchemy для `LISTEN/NOTIFY` — SQLAlchemy не поддерживает этот протокол
- `pg_notify_listener` запускается через `asyncio.create_task()` в `lifespan` FastAPI и живёт весь цикл приложения
- Оффлайн-юзеры не теряют уведомления: `NotificationRecipient` записи создаются всегда, WS-пуш делается только если `manager.is_online(user_id) == True`
- При загрузке страницы фронт получает актуальный счётчик через HTTP `/unread-count`, WS используется только для новых уведомлений в реальном времени
- Browser WebSocket API не поддерживает кастомные заголовки — JWT передаётся как query-параметр `?token=...`
- `bulk_create_recipients_if_not_exists` использует `ON CONFLICT (notification_id, recipient_id) DO NOTHING` — требует уникального constraint на junction-таблице
- `ConnectionManager` — singleton, импортируется и в router (connect/disconnect) и в listener (send_to_user), работает через кэш импортов Python
